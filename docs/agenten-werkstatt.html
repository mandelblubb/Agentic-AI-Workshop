Agenten-Werkstatt

Der Workshop läuft in zwei Gruppen: die einen bauen mit dem Agenten die Anwendung, die anderen bauen Werkzeuge für ihn. Drei Module gelten für beide, die übrigen gehören je einer Gruppe. Fangt links beim Wegweiser an.

Was hier liegt — und wo ihr anfangt

Das Repository enthält zwei Dinge nebeneinander: eine kleine Anwendung, an der gearbeitet wird, und den Agenten, der daran arbeitet. Beides lässt sich erweitern — und je nach Gruppe fasst ihr die andere Hälfte gar nicht an. Filtert auf eure Gruppe, dann bleibt übrig, was euch betrifft.

Gruppe A So fangt ihr an

  1. Setup prüfen. pytest muss 6 passed melden. Wenn nicht: erst das klären, alles andere wartet.
  2. Lest AGENTS.md — zwei Minuten. Das sind die Regeln, an denen ihr den Agenten später messt.
  3. ISSUE-01 öffnen und Muster 2 aus docs/PROMPTS.md als Auftrag geben. Nicht selbst formulieren, das kostet nur Zeit.
  4. Zuschauen statt wegsehen. Plant er, bevor er ändert? Führt er die Tests wirklich aus? Das ist die eigentliche Übung.
  5. Selbst prüfen. git diff lesen und die zwölf Akzeptanzkriterien durchgehen — bevor ihr ihm glaubt.

Gruppe B So fangt ihr an

  1. Setup prüfen. pytest muss 6 passed melden, und die App sollte laufen: uvicorn src.api:app --reload.
  2. Einen Weg wählen — siehe Modul „Sechs Wege". Command oder Skill sind der leichteste Einstieg, der MCP-Server der aufwendigste.
  3. Erst das vorhandene Beispiel laufen lassen, bevor ihr etwas Eigenes baut. Dann wisst ihr, wie „funktioniert" aussieht.
  4. Klein bauen und wirklich testen. Eine Erweiterung, die läuft, ist mehr wert als drei halbfertige.
  5. templates/ mitnehmen. Das ist der Teil, der auch nächste Woche im eigenen Projekt noch nützt.

      Sechs Wege, den Agenten zu erweitern
      
    
      Sie werden regelmäßig verwechselt, und die Namen helfen nicht.
      Wählt aus, was ihr erreichen wollt — der passende Weg wird hervorgehoben.
      Fünf davon beeinflussen, was das Modell denkt. Einer nicht: Ein Plugin läuft
      als Code, ob das Modell daran denkt oder nicht.
      

    
      

    
        

    
        „Hook" ist kein OpenCode-Begriff — einen Schlüssel
      hooks gibt es nicht. Was anderswo so heißt, ist hier ein Plugin;
      die Hook-Namen sind die Ereignisse darin.

          Erst der Plan
          
    
          Ein Agent füllt jede Lücke in der Aufgabe selbst — schnell, plausibel und
      ohne nachzufragen. Die Frage ist nicht, ob er Annahmen trifft, sondern wo ihr sie vorher
      festlegt. Klickt links auf eine erfundene Entscheidung; rechts leuchtet auf, was sie
      verhindert hätte.
          

    
          
      
          
        
          
          
          „Teilnehmer sollen sich zu Veranstaltungen anmelden können."
            So wird ein Ticket meistens formuliert. Fachlich nicht falsch — nur unvollständig.
          
        
          

        
          Was der Agent daraus macht
          
        
          Keine dieser Entscheidungen ist unvernünftig. Sie steht nur nirgends geschrieben.
          
        
            
      
            

      
            
        
            Was ihn davon abgehalten hätte
            
        
            Drei Ebenen, von dauerhaft bis einmalig.

              •

              •
